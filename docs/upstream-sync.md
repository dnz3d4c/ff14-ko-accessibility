# 업스트림 동기화

- 작성: 2026-08-18
- 이 문서가 **동기화 규칙의 단일 원천**이다. [status.md](status.md)와 [ko-client-port-feasibility.md](ko-client-port-feasibility.md) §12는 여기를 가리키기만 한다.
- 한국어 변경 이력은 [upstream-changes.md](upstream-changes.md)가 따로 갖는다.

## 1. 문제가 무엇인가

업스트림([derbruedi/ff14-accessibility](https://github.com/derbruedi/ff14-accessibility))은 **주 30커밋에 거의 매일 릴리스**다. 우리 패치 10건은 그 위에 얹혀 있다. 세 가지가 동시에 걸린다.

1. **밑바닥이 우리가 안 볼 때도 움직인다.** 이 문서를 쓰는 사이에도 하루 만에 태그 2개(v5.86, v5.87)와 커밋 5건이 늘었고, 바뀐 파일 10개 중 3개가 하필 우리 패치가 건드리는 파일이었다.
2. **우리 저장소에는 "지금 어느 판 위에 있는지"가 안 적혀 있었다.** `vendor/`는 `.gitignore`라 버전 관리 밖이다. 다른 머신에서 클론한 사람은 그날의 `main` 위에 패치를 붙이게 되고, **붙는 자리가 다르다는 것을 아무도 모른다.**
3. **업스트림은 독일어로 개발된다.** 커밋도 릴리스 노트도 독일어라, 뭐가 들어왔는지 그대로는 **읽을 수가 없다.**

셋 다 조용히 실패한다. 그래서 규칙이 아니라 **검사기**로 막는다.

| 무엇을 | 무엇이 막나 |
|--------|-------------|
| 붙는 자리가 흔들리는 것 | `upstream.json` + `tools/patch-check` |
| 업스트림이 앞서 간 것을 모르는 것 | `run\sync.bat` + [주 1회 감시](../.github/workflows/upstream-watch.yml) |
| 이력이 독일어로만 남는 것 | `(미번역)` 표시 + pytest + 커밋 훅 C10 |
| 문장이 늘어난 걸 모르는 것 | `tools/strings-golden` |

## 2. 핀 — 지금 어디에 얹혀 있나

`upstream.json`이 그 자리다.

```json
{
  "commit": "30512023e7a69683c02655506b29a7c53d2d21d5",
  "repo": "https://github.com/derbruedi/ff14-accessibility.git",
  "synced": "2026-08-18",
  "tag": "v5.85"
}
```

**패치는 `main`이 아니라 이 커밋에 붙는다.** `main`은 클론한 날짜에 따라 다른 것을 가리키므로 기준이 될 수 없다. `tools/patch-check`가 이 커밋 위에 패치를 붙여 보고, 결과가 vendor의 `kr-port`와 같은 트리인지 확인한다.

핀을 옮기는 것은 `tools/upstream-sync` **하나뿐이다.** 손으로 고치지 않는다.

`vendor`를 submodule로 전환하면(status.md `W-11`) 핀은 submodule 포인터가 대신한다. 그때 이 파일은 사라진다.

## 3. 로컬에서 일할 때

`vendor/`는 우리 저장소 밖이다. 그래서 **거기서 한 일은 우리 저장소에 아무 증상도 안 남긴다.** 세 가지가 어긋날 수 있고, 셋 다 검사한다.

| 어긋남 | 증상 | 무엇이 잡나 |
|--------|------|-------------|
| vendor에 커밋해 놓고 패치를 안 뽑음 | 다음에 클론한 사람이 다른 물건을 빌드한다 | pre-commit 훅 (개수) |
| 패치를 뽑은 뒤 vendor에서 더 손댐 | 패치와 실제 빌드가 다르다 | `run\check.bat` (트리 비교) |
| vendor의 `main`을 혼자 올림 | 붙는 자리가 핀과 달라진다 | 핀 기준 검사 (§2) |

**vendor에서 직접 작업하지 않는다.** `kr-port` 브랜치에 커밋하고 `git format-patch`로 떼어낸다. 절차는 [overlay/patches/README.md](../overlay/patches/README.md).

클론이 없는 머신에서는 검사를 **건너뛴다.** 오류가 아니다 — 클론이 없는 사람에게 빨간불을 띄우면 아무도 안 본다.

## 4. 언제 올리나

**태그 단위로만 움직인다.** 커밋 단위로 쫓으면 따라잡는 일이 본업이 된다.

- **주 1회** 감시가 돈다(월요일 07:00 KST). 새 태그가 있으면 이슈가 열린다.
- **작업을 시작하기 전에** `run\sync.bat`으로 한 번 본다. 번역 같은 큰 작업 도중에 밑바닥이 움직이면 되돌리기가 비싸다.
- **번역을 시작하기 직전에는 반드시 올린다.** 안 그러면 676쌍을 옮긴 뒤에 새 문장이 또 나온다.

무조건 최신으로 끌려가지 않는다. `run\sync.bat`은 인자 없이는 **아무것도 안 옮긴다.** 올릴 태그를 손으로 적게 해서, 실수로 최신에 끌려가는 일을 막는다.

## 5. 어떻게 올리나

### 5.1 점검 — 아무것도 안 옮긴다

    run\sync.bat

받아오고 재기만 한다. 나오는 것: 새 태그, 새 커밋 수, 바뀐 파일 중 **우리 패치와 겹치는 것**, 그리고 **우리 패치가 새 태그에 아직 붙는가.**

마지막 항목이 조기 경보다. 겹치는 파일이 있어도 붙으면 대개 문제가 없고, 안 붙으면 그때가 손이 필요한 시점이다.

### 5.2 깨끗할 때 — 도구가 한다

    run\sync.bat v5.87

이 경우가 대부분이다. 도구가 하는 일:

1. **먼저 임시 워크트리에서 붙여 본다.** 하나라도 어긋나면 **아무것도 건드리지 않고** 멈춘다
2. 되돌릴 자리를 만든다 (`kr-port-<이전태그>` 브랜치)
3. `main`과 `kr-port`를 새 태그로 옮기고 패치를 다시 붙인다
4. `git format-patch`로 패치를 다시 뽑는다 — 부모가 바뀌었으므로 패치 파일도 바뀐다
5. 핀을 갱신한다

**여기까지가 도구의 몫이다.** 남는 것은 이 순서로 한다.

1. 변경 이력을 한국어로 (§6)
2. 골든 대조 (§7)
3. `run\check.bat` — 테스트·패치 정합성·양쪽 빌드
4. **인게임 확인 — 사용자 몫이다.** 기계는 여기까지 못 온다

### 5.3 안 붙을 때

도구가 멈추고 **처음 실패한 패치 이름**을 알려 준다. 그때부터는 손이다.

    cd vendor/ff14-accessibility
    git checkout -b kr-port-new <새태그>
    git am ../../patches/*.patch ../../overlay/patches/*.patch

충돌한 자리에서 판단할 것은 하나다 — **업스트림이 우리 패치가 하려던 일을 이미 했는가.**

- 했으면 그 패치는 **사라진다.** 특히 `patches/`(업스트림에 보낼 것)가 줄어드는 건 좋은 신호다
- 아니면 새 코드에 맞춰 다시 쓴다
- 다시 붙인 뒤 `git format-patch`로 뽑고 핀을 손으로 맞춘다

## 6. 변경 이력을 한국어로

**이게 동기화의 필수 단계다.** 원문이 독일어라, 옮기지 않으면 우리 저장소에 뭐가 들어왔는지 읽을 수 있는 사람이 없다.

    uv run --no-project python tools/upstream-sync/upstream_sync.py --notes

도구가 [upstream-changes.md](upstream-changes.md)에 **원문과 함께 `(미번역)` 자리**를 만든다. 채우는 것은 사람이다. 기계 번역을 붙이지 않는다 — 이 저장소는 게임 용어를 지어낸 전례로 한 번 다쳤다(2026-08-18 `Aetheryte`).

지킬 것 셋.

1. **원문을 지우지 않는다.** 옮긴 게 틀렸을 때 되짚을 자리가 그것뿐이다
2. **모르는 게임 용어는 원문을 병기하고 `용어 미확인`이라고 적는다.** 한국어판 표기를 확인하기 전에는 결정이 아니다
3. **릴리스마다 "우리 쪽" 한 줄을 적는다** — 패치가 그대로 붙었는지, 새 안내 문장이 몇 개인지

**`(미번역)`이 남아 있으면 검사가 통과하지 않는다.** `tools/upstream-sync/tests`가 막고, `run\check.bat`이 그 테스트를 돌린다. 그리고 커밋 훅 C10이 핀만 옮기고 이력을 안 남긴 커밋을 거부한다.

## 7. 번역이 밀리는 것

업스트림이 안내 문장을 더하면 **한국어화 대상이 그만큼 늘어난다.** 예: v5.86이 5개를 더했다.

    uv run --no-project python tools/strings-golden/strings_golden.py

동기화 직후에는 이 대조가 반드시 빨개진다. 두 경우를 구분해서 읽는다.

| 결과 | 뜻 | 할 일 |
|------|-----|-------|
| 사라진 문장 0, 새 문장 N | 업스트림이 더한 것뿐 | `--write`로 갱신. 새 N개를 번역 대상에 더한다 |
| 사라진 문장 있음 | 업스트림이 문장을 **고쳤거나** 우리가 옮기다 떨어뜨렸다 | 갱신 전에 그 줄을 찾는다 |

도구가 이 판정을 직접 찍어 준다. 갱신은 판단 뒤에 한다 — `--write`를 먼저 누르면 증거가 사라진다.

스냅샷 **밖**에 있는 것은 아직 지켜지지 않는다. `CharaMakeIconText`·`CharaMakeShapeText` 튜플 사전 3,023건이 거기다(status.md §5).

## 8. 커밋

동기화 커밋은 `[벤더]`다. 현황판은 요구하지 않는다 — 업스트림 포인터를 옮기는 것 자체는 할 일의 이동이 아니다.

**우리 쪽 수정이 필요 없었던 깨끗한 동기화**의 본보기.

```
[벤더] 업스트림 v5.87로 올림 - 우리 쪽 수정 없음

패치 10건이 새 태그에 그대로 붙었다. 충돌 0건.

붙임: 패치 10건 전부 (patches 2, overlay 8)
빌드: KR 7.51 경고 0 오류 0 / 글로벌 7.55 경고 0 오류 0
테스트: 176 통과
문장: 676쌍 -> 681쌍 (새 5개, 사라진 것 0 - 골든 갱신)
인게임: 안 함

Upstream-Range: v5.85..v5.87 (3051202..a8ac7c5)
```

`Upstream-Range`는 **필수다**(훅 C9). 이게 없으면 "이 판에서 뭐가 들어왔나"를 되짚을 수 없다.

패치를 다시 쓴 경우에는 `[벤더]`로 묶지 않는다. 핀 이동은 `[벤더]`, 다시 쓴 패치는 원래 갈래(`[업스트림]`·`[한국전용]`)로 나눈다. 섞으면 나중에 보낼 것만 떼어낼 수 없다 — [commit-rules.md](commit-rules.md) §0.

## 9. KR 쪽이 움직일 때

동기화는 위에서만 오지 않는다. **아래에서도 온다.** 업스트림과 무관하게 우리만 깨질 수 있는 자리다.

| 무엇이 움직이나 | 왜 우리가 깨지나 | 무엇이 잡나 |
|-----------------|------------------|-------------|
| KR 클라이언트 게임 패치 | 시그니처가 안 잡히거나 둘 이상 잡힌다 | `tools/sig-probe` |
| KR Dalamud 갱신 | `Hooks` 폴더 이름이 버전이라 바뀐다 | `run\_env.cmd`가 최신을 자동 선택 |
| FFXIVClientStructs 버전 | KR은 7.51 고정, 업스트림은 7.55. 짝이 어긋나면 **적재는 되고 호출에서 던진다** | `tools/asmref-check` + `run\check.bat`의 양쪽 빌드 |
| vnavmesh 갱신 | 남의 플러그인 IPC 15종이 우리 자동이동 전부다 | `tools/asmref-check` |

**게임이 패치되면 업스트림 동기화보다 이쪽이 먼저다.** 순서는 이렇다.

1. KR Dalamud 업데이터로 갱신
2. `run\check.bat` — 여기서 CS 버전 짝이 깨지면 빌드가 먼저 죽는다
3. 통과하면 그다음이 업스트림 동기화

이 계층은 **우리가 통제하지 못한다.** `MiqoKR/*`는 단독 메인테이너에 버스 팩터 1이고, 그게 멈추면 우리 포팅 전체가 멈춘다(조사 §12 위험 1). 완화책은 하나뿐이다 — **우리 산출물을 데이터 위주로 유지해서** Dalamud 계층이 갈릴 때 재작업을 줄인다.

## 10. 주기 감시

[.github/workflows/upstream-watch.yml](../.github/workflows/upstream-watch.yml)이 주 1회 돈다. 하는 일은 **알리는 것뿐이다.**

- 업스트림을 클론해서 `--json`으로 재고, 새 태그가 있으면 이슈를 연다(태그당 하나)
- 이슈에는 **독일어 원문 그대로** 싣는다. 러너에는 옮길 수단이 없다
- 아무것도 옮기지 않는다. **올리려면 KR Dalamud로 빌드하고 인게임에서 들어 봐야 하는데 러너에는 게임도 KR Dalamud도 없다**

여기서 판정할 수 있는 것은 "우리 패치가 새 태그에 아직 붙는가"까지다. 그게 조기 경보로는 충분하다.

**판정도 이슈 본문도 전부 도구가 만든다.** 워크플로는 도구를 부르고 결과를 옮기기만 한다 — 러너에만 있는 도구로 CI 안에서 조립하면 개발 머신에서 돌려 볼 수가 없고, **못 돌려 보는 코드는 처음 필요한 날 깨져 있는다.** 이슈 본문은 `tools/upstream-sync/tests`가 검사한다.

    uv run --no-project python tools/upstream-sync/upstream_sync.py --issue-body

새 태그가 없으면 아무것도 안 찍는다. 워크플로는 그 빈 출력을 보고 이슈를 안 연다.

## 11. 명시적으로 하지 않는 것

- **자동 병합·자동 커밋.** 인게임 확인 없이 올린 것은 확인된 게 아니다. 도구는 로컬에서 사람이 부를 때만 옮긴다
- **커밋 단위 추종.** 태그 단위다(§4)
- **기계 번역으로 이력 채우기.** 용어를 지어내는 것보다 `(미번역)`이 낫다
- **업스트림 fork 유지.** 보낼 것은 `patches/`에 쌓고 PR 시점에 조립한다([commit-rules.md](commit-rules.md) §5)

## 12. 건강 지표

동기화가 잘 되고 있는지는 숫자 둘로 본다.

1. **`patches/`가 줄어드는가.** 우리가 올린 일반화가 병합되면 줄어든다. 안 줄고 늘기만 하면 원본에서 멀어지는 중이다
2. **핀과 최신 태그의 거리.** `run\sync.bat`이 매번 찍는다. 태그 여러 개가 쌓이면 한 번에 올리는 비용이 커진다
