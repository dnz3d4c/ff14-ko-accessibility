# vendor를 submodule로 옮긴다 (W-11)

- 착수: 2026-08-19
- 이 문서는 **왜 옮기는지와 어떻게 옮기는지**를 갖는다. 남은 일의 순서는 [현황판](../status.md) §2가 갖는다.

## 1. 무엇을 바꾸나

`vendor/ff14-accessibility`는 지금 **버전 관리 밖의 클론**이다(`.gitignore`). 우리 저장소는 `upstream.json`의 핀과 패치 파일 16개를 갖고, 빌드할 때마다 핀 위에 패치를 다시 붙여 `kr-port` 브랜치를 만든다.

바꾸는 것은 **원본이 어디냐**다.

| | 지금 | 바꾼 뒤 |
|---|------|---------|
| 원본 | `patches/`·`overlay/patches/`의 패치 파일 16개 | `kr-port` 브랜치의 커밋 16건 |
| 우리 저장소가 기록하는 것 | 핀(업스트림 커밋) + 패치 파일 | 핀 + **gitlink**(`kr-port` 팁을 가리키는 커밋 포인터) |
| 둘이 어긋나는 것을 막는 것 | `tools/patch-check`가 매번 붙여 보고 트리를 대조 | **git 자신** |

## 2. 왜 지금인가

**업스트림 속도가 이유다.** 2026-08-19 실측이다.

- 첫 태그 `v4.58.0`(2026-07-12)부터 `v5.88`(2026-08-18)까지 **37일에 태그 51개**. 하루 1.38개
- **최근 7일 6개, 최근 14일 12개.** 감속 신호가 없다

여기에 우리 정책(태그 단위·주 1회, [sync.md](sync.md) §4)을 곱하면 **연 52회 동기화**다. 한 번에 패치 16개를 다시 뽑고, 그 재생성 소음이 커밋마다 14파일 180줄씩 이력에 쌓인다(v5.88 동기화 커밋 `bbc9470` 실측). 연 52회면 약 9,000줄이다.

**그리고 미루면 비싸진다.** 패치 파일을 읽는 코드가 늘고 있다.

| 시점 | 패치를 읽는 자리 |
|------|------------------|
| 처음 | `patch-check` 하나 |
| 2026-08-19 | **9곳 + CI 1곳** |

최근에 생긴 셋(`tools/ko-words/ko_words.py`, `tools/docs-check/docs_check.py:49`, `tools/sig-probe`의 테스트)이 전부 W-20·W-32 작업에서 붙었다. **대략 월 1~2곳씩 선형으로 는다.** 전환 비용은 패치 개수가 아니라 이 결합 지점 수에 비례한다.

## 3. 패치 파일을 지우는 쪽을 골랐다

전환에는 두 갈래가 있었고, 갈라지는 자리는 **패치 파일을 생성물로 남기느냐 없애느냐**였다.

**남기는 쪽은 안전하지만 관리 지점이 는다.** 소비자 코드가 전부 무변경이라 일회 비용이 거의 0인 대신, 같은 사실의 표현이 셋(`kr-port` 커밋·gitlink·패치 파일)이 되고 셋을 묶는 검사기를 우리가 계속 갖고 있어야 한다. 미러 저장소·pre-push 훅·`refs/keep`이 새로 생기는데 없어지는 것은 하나도 없다.

**없애는 쪽을 골랐다.** 견적이 예상과 반대였다.

| | 줄 수 |
|---|-------|
| 추가되는 코드 | 약 40 |
| 삭제되는 코드 | 약 495 |
| **순감** | **약 450** |

삭제분의 대부분(`patch_check.py` 226줄 + 그 테스트 223줄)이 **"패치와 `kr-port`가 어긋났다"는 사고 모드**를 잡는 코드다. 원본이 하나가 되면 그 사고 자체가 존재하지 않는다.

**막는 것은 없었다.** 소비자 10곳을 하나씩 확인했고 전부 git 연산이나 `kr-port` 워킹트리 직독으로 대체된다. `docs_check.py`와 `ko_words.py`는 이미 diff를 파싱하고 있어서 **입력 소스만 바뀐다.**

## 4. 버린 갈래와 그 이유

| 갈래 | 왜 안 하나 |
|------|-----------|
| gitlink이 **업스트림 태그**를 가리킨다 | 하는 일이 지금 핀과 똑같다. 패치는 여전히 `git am`으로 붙여야 하고, 붙이는 순간 gitlink에서 벗어나 상위가 영구히 더러워진다 |
| `git subtree` | C# 소스 전체가 우리 저장소 안에 실재하게 된다. 그리고 충돌이 패치 단위가 아니라 병합 단위로 와서, **`0008`은 풀지 않고 다시 만든다**는 설계([sync.md](sync.md) §5.4)가 근거를 잃는다 |
| NuGet 등 패키지 참조 | `FF14Accessibility.csproj`는 DalamudPackager로 포장되는 플러그인 실행물이고 패키지 발행 설정이 없다. 우리 패치 15건이 내부를 고치는 것이라 확장점으로 대체될 성질이 아니다 |
| 아카이브·번들 고정 | 패치가 이미 같은 정보를 **읽을 수 있는 텍스트**로 갖고 있었다. 리뷰가 안 되는 이중 표현이 하나 느는 것이다 |

## 5. 원격은 fork가 아니라 비공개 미러다

gitlink은 **원격에서 받아올 수 있는 커밋**을 가리켜야 한다. 그런데 `kr-port` 팁은 2026-08-19까지 **어느 원격에도 없었다** — 이 디스크가 유일한 사본이었고, 원격에 없는 커밋이 78건이었다.

그래서 `dnz3d4c/ff14-accessibility-mirror`(비공개)를 만들고 전부 올렸다.

**GitHub fork 버튼을 쓰지 않았다.** 업스트림이 공개 저장소라 fork도 공개가 강제되는데, 그러면 인게임 판정이 안 끝난 한국어가 남의 눈에 띄고 태그마다 도는 force-push가 공개 이력에 남는다.

**[sync.md](sync.md) §11의 "업스트림 fork에 이력을 쌓지 않는다"와 부딪히지 않는다.** 그 조항이 가리키는 것은 **PR 조립 경로**다 — 보낼 것은 표시만 해 두고 PR 시점에 fork 브랜치로 조립한다. 미러는 fork 네트워크 밖이고, PR 재료를 담지 않으며, 업스트림에서 보이지 않는다.

**밑동도 같이 구했다.** 태그를 함께 밀어서 핀 커밋이 미러에 들어갔다. 전에는 그 커밋이 업스트림 GitHub와 이 디스크에만 있었으므로, 업스트림이 사라지면 패치 16건은 **붙을 자리가 없는 종잇장**이 되는 상태였다.

## 6. 남는 위험

**`kr-port`는 태그마다 다시 쌓인다**(`tools/upstream-sync/upstream_sync.py`의 `cmd_to`). 옛 팁을 가리키던 gitlink은 그때 갈 곳을 잃는다. 그래서 우리 저장소가 기록한 gitlink은 **전부 이름 있는 참조로 미러에 남겨야 한다** — 도달성 추론에 기대지 않는다.

**업스트림에 보낼 것과 우리 것의 경계가 약해진다.** 전에는 `patches/`와 `overlay/patches/`가 물리적으로 갈려 있어서 커밋 훅 C7이 섞이는 것을 막았다. 패치가 없어지면 그 경계가 `kr-port` 안의 커밋 위치가 되는데, 커밋에 갈래를 밝히는 표시가 없다. 어떻게 할지는 판의 `## 7`에 올렸다(D-7).

**CI가 비공개 미러에 접근해야 한다.** 주간 감시(`.github/workflows/upstream-watch.yml`)가 "우리 것이 새 태그에 아직 붙는가"를 판정하는데, 지금은 저장소 안의 패치를 읽어서 한다. 읽기 전용 deploy key를 쓴다 — 만료가 없어 회전 비용이 0이다.
