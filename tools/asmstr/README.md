# asmstr — 남의 플러그인이 한국 클라이언트에서 함수를 찾을 수 있는지 미리 본다

Dalamud 플러그인은 게임 함수를 바이트 시그니처(AOB 패턴)로 찾는다. 그 패턴은 **한 클라이언트 빌드를 보고 쓴 것**이라, 글로벌판용 플러그인(vnavmesh 등)을 한국 클라이언트에 얹으면 패턴이 안 잡히거나 엉뚱한 곳에 잡힐 수 있다.

**게임을 켜지 않고** 판정한다. 패턴은 어셈블리 안에 평범한 문자열 리터럴로 들어 있고, 그 패턴이 찾는 바이트는 `ffxiv_dx11.exe` 파일 안에 있다. 둘 다 정적으로 읽을 수 있다.

## 도구

### `extract_sigs.py` — 어셈블리에서 시그니처 문자열을 뽑는다

uv run --no-project python tools/asmstr/extract_sigs.py "<플러그인.dll>"

`--json`을 주면 JSON 배열로 낸다. 뽑는 기준은 "토큰이 전부 2자리 16진수이거나 `?`/`??`이고, 8개 이상". Dalamud의 `SigScanner`가 받아들이는 문법 그대로다.

### `classify.py` — 뽑은 시그니처를 게임 바이너리에 대고 판정한다

uv run --no-project python tools/asmstr/classify.py "<게임.exe>" "<플러그인.dll>" --cache "<cs.json>"

| 판정 | 뜻 |
|------|-----|
| UNIQUE | 한 군데. 플러그인이 찾는 것을 찾는다 |
| NOT FOUND | 0건. `ScanText`가 예외를 던지고 그 훅은 죽는다 |
| AMBIGUOUS | 2건 이상. `ScanText`는 첫 번째를 쓰는데, 그게 맞는 함수라는 보장이 없다 |

**이 판정은 관문이 아니다.** `classify.py`는 `NOT FOUND`가 나오든 `AMBIGUOUS`가 나오든 항상 0으로 끝나고(`main`의 `return 0`), `run\check.bat`은 이 도구를 부르지 않는다 — 거기서 도는 것은 `tools` 아래 pytest뿐이라 **판정기가 고장 나지 않았는지**만 지킨다. 빨간불을 기다리지 말고 **출력을 사람이 읽어야 한다.** 사람이 고쳐야 하는 신호는 `UNIQUE`가 아닌 줄 전부다.

스캔 자체는 `tools/sig-probe/sig_probe.py`가 한다(이미 검증된 물건이다). exe는 **한 번만 읽어** 메모리에 올리고 모든 시그니처를 그 위에서 대조한다.

## `#US`와 `#Blob`을 둘 다 읽어야 하는 이유

문자열 리터럴이 **두 군데**에 나뉘어 들어간다.

- `ScanText("...")`처럼 코드가 직접 부르는 패턴 → `#US` 힙에 UTF-16
- `[Signature("...")]` 어트리뷰트로 선언한 패턴 → **`#Blob` 힙에 UTF-8**. 어트리뷰트 인자는 인터닝이 아니라 직렬화라서 문자열 힙에 안 들어간다

vnavmesh는 양쪽을 다 쓴다. `#US`만 읽었을 때 6개 중 3개만 나왔고, **나머지 3개는 존재 자체가 안 보이니 "이상 없음"으로 통과할 뻔했다.** 이게 이 도구에서 제일 쉽게 놓치는 함정이다.

`#Blob`은 어트리뷰트 생성자 시그니처를 모르면 구조를 따라갈 수 없어서, 모든 오프셋을 길이 접두사로 시도하는 방식으로 읽는다. 그 부작용으로 진짜 패턴의 꼬리가 또 하나의 패턴처럼 파싱되므로 `drop_contained`가 포함관계를 걸러낸다.

## 대조군이 왜 그 둘인가

"전부 UNIQUE"라는 결과는 **판정기가 고장 나서 UNIQUE만 뱉는 경우와 구분이 안 된다.** 그래서 답을 미리 아는 입력을 같이 돌린다.

1. **`FF14Accessibility.dll` (우리 플러그인)** — 한국 실기에서 동작이 증명된 물건이다. 여기서 NOT FOUND가 나오면 원인은 대상 플러그인이 아니라 **추출기나 판정기 쪽**이다.
2. **`cachedSigs/cs.json` 표본** — Dalamud가 실제 게임 프로세스에서 해석에 **성공해서** 캐시해 둔 시그니처다. 전부 UNIQUE로 나와야 정상이다. (`+relfollow[...]` 항목은 함수가 아니라 정적 객체를 가리켜서 제외한다.)

두 대조군은 "거짓 NOT FOUND"만 잡는다. 반대 방향, 즉 판정기가 UNIQUE에 붙박이가 된 경우는 `tests/test_classify.py`가 잡는다 — 한국 바이너리에 없는 것이 확인된 패턴으로 NOT FOUND를, 흔한 함수 프롤로그로 AMBIGUOUS를 실제로 만들어 본다.

## 이 도구가 말하지 않는 것

- UNIQUE는 "`ScanText`가 성공하고 실제 함수를 가리킨다"까지만 증명한다. **글로벌판과 같은 함수인지는 증명하지 않는다.** 다른 빌드에서 다른 함수가 같은 패턴을 유일하게 가질 수 있다.
- 플러그인이 FFXIVClientStructs를 거쳐 접근하는 부분은 대상이 아니다. **구조체 필드 오프셋이 한국 클라이언트에서 맞는지는 여기서 아무 말도 하지 않는다.**
- 런타임에 조립되는 시그니처(문자열 연결, 설정 파일에서 읽기)는 원리상 안 잡힌다.
